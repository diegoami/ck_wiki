# ck_wiki — the published CK3 chronicles

This repository publishes the Crusader Kings III wikis and holds the images
they are waiting for. It is where two other projects meet:

| Project | What it puts here |
|---|---|
| [`diegoami/Ck-parser`](https://github.com/diegoami/Ck-parser) | the code that reads the saves and writes the pages |
| [`diegoami/ck_portrait_generator`](https://github.com/diegoami/ck_portrait_generator) | the harvested portraits and coats of arms, committed to `images/` |

Neither imports the other. They agree on file names and nothing else.

## What is in git, and what is not

```
images/            every harvested image, flat, named as below
portraits.json     what the wiki wants, across all chronicles
<chronicle>/portraits.json    the same, per chronicle
```

The pages themselves are **not** committed. They are built on every run from
the parser plus the saves attached to Ck-parser's Releases, and published as a
Pages artifact, so a rebuild is never a five-thousand-file diff. The manifests
*are* committed, because they are the companion's work queue and it should be
able to read them straight from git.

## Adding an image

Commit it to `images/`. That is the whole procedure.

Every page links every image it expects whether or not the file exists: a
missing one renders as a dashed slot marked *awaiting harvest*, and its `src`
already points at the right name. So pushing the file is publishing it —
nothing is regenerated by hand, no link changes, and the next build simply
finds it. Pushing to `images/` triggers that build.

Names are **derived** by both sides, never assigned, from the save's base name
and the id:

```python
import hashlib
from pathlib import Path

def save_checksum(save_file: str) -> str:
    return hashlib.sha256(Path(save_file).name.encode("utf-8")).hexdigest()[:12]

def portrait_name(save_file: str, character_id: int) -> str:
    return f"{save_checksum(save_file)}_{character_id}.png"

def arms_name(save_file: str, coat_of_arms_id: int) -> str:
    return f"{save_checksum(save_file)}_arms_{coat_of_arms_id}.png"
```

The save file's *name* is hashed, not its contents, so either side computes it
without opening 70 MB. Keying on the save rather than the date is what gives a
character one portrait **per save**: the same person at three dates is three
images. Arms are scoped by save for a different reason — a `coat_of_arms_id` is
an index inside one run, so the same number means different arms in a parallel
world.

`images/` is flat and shared: the names already carry the save, so nothing
collides, and the build copies each chronicle only the images it links.

## Finding what is missing

`portraits.json` at the root lists the chronicles; each chronicle's own copy
lists every image it wants:

```json
{ "file": "5a86b836cd32_50544311.png", "kind": "portrait",
  "save": "Fylkir_Ludwig_of_Immasonian_Fylkirate_1364_03_10.ck3",
  "checksum": "5a86b836cd32", "save_date": "1364.3.10",
  "character": 50544311, "house": 4981,
  "page": "characters/50544311.html", "have": false }
```

`kind` is `portrait` or `arms`. `have` is one build's answer, not a promise —
treat the file's absence as the truth and the flag as a hint. `saves` in each
chronicle repeats the save-to-checksum map, so the companion can check its own
against it rather than trust ours. Character names are never written here; the
companion drops them on principle.

## One chronicle per playthrough

A chronicle is one game, identified by its random seed and the game version it
was started on — never by the title it happens to be about. Saves are grouped
into runs automatically, so attaching a save from a different game to
Ck-parser's Releases adds a chronicle here with no configuration.

## Rebuilding

Pushing to `images/` rebuilds. So does the weekly schedule, which is what picks
up saves attached during the week. `workflow_dispatch` takes an optional
Ck-parser ref, for trying a branch before it lands.
